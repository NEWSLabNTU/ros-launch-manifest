### 1a. Topic wiring vs remaps (`derive_topics_from_remaps`, `manifest_loader.rs:6724-6815`)

What the derivation gives and does not:

1. **Only remapped endpoints.** It walks `record.remaps` (`:6737-6738`); a
   node that publishes on a name compiled into its source has no remap and no
   derived edge.
2. **Only the convention's direction.** `remap_direction` decides from
   `input`/`output`/`/diagnostics`; anything else is counted `ambiguous` and
   dropped (`:6743-6746`). Phase 77 measured Autoware's services spelled like
   topics (`~/output/…/operate`) — one appears below.
3. **Not the contract's endpoint name.** The derived endpoint is the remap key
   flattened (`:6747-6754`: `~/input/odometry` → `input_odometry`); a
   contract's endpoint is its `pub.<ep>`/`sub.<ep>` key. Autoware: contract
   `mrm_handler/operation_mode_availability` vs derived
   `/system/mrm_handler/input_operation_mode_availability`. Every endpoint
   property (`max_age`, `on_violation`, `state`, `link`, …) is keyed by the
   contract name, so deleting `topics.pub/sub` needs a new binding from
   endpoint key to remap key — a grammar addition, not a deletion.
4. **Contract always wins; nothing compares.** A declared topic is skipped
   (`:6783-6787`), so there is no agreement check today.

Measured availability (resolve each contract's sibling launch file with
`--no-provider-contracts` and read `structure.topics`; `wiring.py`):

| Corpus | Contracts with a launch file | Launch files with a real `<remap>` | Contracted topics with wiring | …with any remap-derived edge |
|---|---|---|---|---|
| rlm fixtures | 0 (bare manifests) | — | — | — |
| play_launch fixtures + rt_av_demo + rt_workspace | 147 | **0** | 258 (87 resolvable) | **0** |
| safety island | 1 | **0** (launch header: "nano-ros parses `<remap>` but does not route it … the names here document the contract wiring") | 13 | **0** |
| nano-ros-pl | 33 (4 without launch) | **0** | — | **0** |
| Autoware 1.5.0 overlay (`tests/fixtures/autoware/contracts`, planning_simulator, 371 remaps) | 4 | yes | 8 topics, 10 endpoints | **8 of 8 topics; every contracted node also derived** (one derived edge is a service, phase 77) |

So the derived side exists for Autoware (the one real launch tree in the
corpus) and is complete there at node level, and is absent for every other
contract, including the island, whose target (nano-ros) does not route
remaps by design. Deletion would be lossy for 100% of the non-Autoware
corpus.

## 3. Methods, per key

| Key | M1 agreement first | M2 delete (no reader) | M3 move the fact | M4 keep, stated as consequence |
|---|---|---|---|---|
| `tolerance` | Unneeded: the two keys are definitionally one quantity | **Fits, with a caveat**: `migrate` may only fold `tolerance` into an EXISTING `sync.max_interval` (take the min; refuse on disagreement). Where no `sync:` exists (both corpus uses), rewriting to `sync: {policy: approximate, max_interval}` CHANGES the derived fan-in rate from the SUM of inputs to the MIN (CLAUDE.md phase 68) — not lossless; refuse with a message instead. `sync-budget` keeps working on `max_interval`. Model: drop `tolerance_ms` (read-compatible). Size ~40 lines rlm, ~10 play_launch. | — | — |
| `topics.pub/sub` | **Fits**: emit `derivable-wiring` / `wiring-mismatch` per contracted topic where remaps exist; needs an endpoint-to-remap binding (e.g. the endpoint key equals the remap's `from`, or `pub.<ep>: { remap: ~/output/x }`) | No: derived side absent in every corpus contract but Autoware's 4 | — | Already the situation (contract wins) |
| `topics.rate_hz` | Census exists (2 agree / 16 underivable) | No | **Fits for external**: `external: { side: pub, rate: 10Hz }` (12 uses / 9 files, mechanical `migrate`); internal `rate_hz` then refusable as a consequence **only after** the model carries `derived_rate_hz` as `TopicContract.rate_hz` (or a sibling) and nano-ros reads it | Interim |
| `emits` | — | No (2 consumers in 2 repos) | **Not yet**: lossless only in 14/119; the other 105 need authored predicates or a mode | Keep; optional rule `emits-uncommanded` (info) where a mode exists and does not command the emitted topic, to grow agreement |
| `args.type/choices` | Possible only after the parser records declared `choices` into the dump/model (absent today); `type: bool` has no launch equivalent | No | — | **Fits** (rlm fixtures only; satisfiability is rlm-standalone) |
| `lifecycle` | `derivable-lifecycle` (info) where the launch declares one | No | — | **Fits**: required for composables and `<node>`-launched managed executables on every distribution |
| `buffer: latest` | — | **No**: nano-ros reads explicit `latest` (`queue_depth.rs:407-428`) | — | Keep. Alternative: make absent mean `latest` in nano-ros too, then delete — a nano-ros design change (it deliberately does not) |

Prior art. ROS 2 `message_filters` ApproximateTime has one knob for this
window, `setMaxIntervalDuration` (and ApproximateEpsilonTime one `epsilon`);
no ROS API carries two names for it, which supports one key. For wiring:
`launch_ros` remaps are the *deployment* binding; Nav2 and Autoware nodes
also hard-code defaults in source (Autoware's own launch files remap almost
every `~/input`/`~/output`, which is why phase 76 works there and only there).
AADL separates the component's ports (features) from the connections
declared in the enclosing system — the contract's `pub.<ep>` is the feature,
`topics.pub` the connection; deleting the connection presumes another
source of connections, which only a remapping launch tree provides.

## 5. Open questions

1. `tolerance` where no `sync:` exists: is a path with a stamp-spread
   tolerance and no synchroniser meaningful at all (should it be refused
   outright), or is it an author who forgot `sync:` (should `migrate` add
   one and accept the rate change)?
2. Endpoint↔remap binding for M1 on wiring: implicit (endpoint key equals
   the remap `from`) or explicit (`remap:` on the endpoint)? The implicit form
   renames every contract endpoint in Autoware-style trees.
3. Should the model carry `derived_rate_hz` beside the authored one (two
   fields, provenance kept) or replace it (one field, `sources` says why)?
   The latter matches the phase 94 `ValueSource` pattern.
4. `buffer`: should nano-ros adopt "absent = latest" so the explicit value
   becomes redundant, or is "silence is not a contradiction" the policy?
5. Is `emits` a candidate to become derivable from `commands` in the
   reverse direction (a mode's `commands` topic + the level's chain → the
   emitting endpoint), letting `commands`-carrying files drop `emits`
   (14 uses) while the rest keep it?
