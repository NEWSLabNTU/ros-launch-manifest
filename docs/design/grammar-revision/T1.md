All three `deprecated(...)` rows say "Removed in the next grammar release";
the two type-level ones say "parses for one release" (`types.rs:634`,
`types.rs:870`). v0.1.60 → v0.3.14 is **33 published tags** (all on
2026-10-15 … 2026-11-09), and nano-ros pins v0.3.14
(`nano-ros-pl/Cargo.toml:129-135`), so the §6 condition for R+1 ("a release
carrying R tagged, published, and mirrored by nano-ros") has been met many
times over. **Verified.**

Detail the doc does not state:

- The fifth item is not a field-table row. `reaction: <mode>` is decided by
  *lookup* (`HazardDecl::entry`, `types.rs:903-905`; `resolve_ladder`,
  `manifest_loader.rs:3270-3295`): a mode of the scope wins, else a scope
  path. Refusing it at parse time is impossible without the scope's modes;
  R+1 for it is a consumer error (`value_rules.rs:911-925` turns from
  warning to error), not a `removed` row.
- `migrate`'s topic-transport rewrite is **not total**: when the topic's
  subscribers are declared in another file it cannot place the value and
  reports instead (`migrate.rs:1343`). After R+1 such a contract is refused
  with no automatic fix.
- Its target, `sub.<ep>.max_transport`, is itself on a schedule (below), so
  the migration lands on a spelling that is already "one release of overlap".

Prior art for "a fixed number of releases, then removal, enforced": the
Kubernetes API deprecation policy (removal only after a stated number of
releases per stability tier; https://kubernetes.io/docs/reference/using-api/deprecation-policy/),
and ROS 2's own developer guide (deprecated in one distribution, removed in
the next; docs.ros.org "Developer Guide → Deprecation strategy"). Both
publish the schedule *with* the deprecation, which is what the `deprecated_in`
column of method 2 records.

## 4. Recommendation

- **1a: method 1**, for all five, in one R+1 release, plus the R+1 step-4
  test (one negative case per name). Before it: move
  `contract_values_node_missing` onto a node-level host
  (`nodes.<n>.sub.<ep>.max_transport` or a link) and delete the topic key from
  `contract_transport_notice` (its own header says T1 "takes over" — that
  time has come).
- **`transport-inline` (1b): put it on the schedule now** — a `deprecated`
  row on the subscriber's `max_transport` (R), not an info rule with a
  promise in a comment. Then decide whether topic-transport's `migrate`
  target should be a link directly (two hops of migration are worse than
  one).
- **1c: delete `links.monitor`** (grammar rows, `LinkMonitor`, lowering,
  `LinkMonitorContract`). Phase 97 P5 was not adopted; re-adding a key when a
  consumer exists costs less than carrying a reserved one.
- **Method 2, with a registry for value- and rule-level deprecations**, and
  **method 4** so the census can see the next `monitor`.
