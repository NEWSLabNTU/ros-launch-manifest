# T9. Interfaces without timing: actions and transforms

Explored 2026-11-13 against rlm v0.3.14 and play_launch main (8f29baad).
Probes: `play_launch/tmp/grammar-revision/T9-probe/` (a live run of an action pair and a
static TF publisher under interception, and `check` on an action-on-a-route
variant of the `contract_fault_service` fixture).

## Issues (verified)

### T9a. Actions carry no timing

| Claim in grammar-revision.md | Verdict | Evidence |
|---|---|---|
| "an action has only `call`" | True (plus `type`, `server`, `client`, `external`, `if`, `unless`) | rlm `types/src/field_table.rs:861-897` |
| "a service has `max_response`, `idempotent`, `stale_after`" | True but incomplete: those are SERVER endpoint keys (`srv.<ep>`, `field_table.rs:698-734`); the client side has `call`, `timeout`, `on_timeout`, `on_rejected`, `max_transport` (`field_table.rs:645-668`, 596). The service declaration itself carries only `max_transport` (`field_table.rs:860`). | |
| "a reaction route through an action ... is not charged" | **Overstated in the wrong direction: it is refused, and the fallback understates.** | see below |

What actually happens. The reaction walk crosses topics and `index.services`
only (`resolve/src/ros/manifest_loader.rs:2472-2486`, `2510-2545`); it never
reads `index.actions`. An action declaration is resolved
(`manifest_loader.rs:7062-7135`), lowered into `structure.actions` with the
per-client `call` (`model_builder.rs:1353-1370`), and checked for a missing
server (#0059, `manifest_loader.rs:1197`), nothing else. Probe: the
`contract_fault_service` fixture with its `services:` entry turned into an
`actions:` entry (same refs, same numbers):

| Variant | Verdict | fault-reaction-time |
|---|---|---|
| service (fixture as is) | clean, 2 warnings | 100 + (7 route + 200 settle) = **307 ms** |
| action, client/server keys left under `cli:`/`srv:` | `error[reaction-unreachable]` + 2 `wiring` warnings | 100 + 100 (declared `max_latency`, "no reaction route") = **200 ms** |
| action, no node endpoint keys | same | 200 ms |

So a contract with an action on a reaction route does not pass silently: it
is an error. But the message's fallback ("using its declared max_latency")
drops the 200 ms settle and the criticality derivation stops at the action
boundary, so the printed number is 107 ms below the truth. Also, nothing
refuses an action's client named under `cli:` (variant 2 parses).

Grammar gap underneath: there is no node-level endpoint map for actions.
`srv:`/`cli:` exist (`field_table.rs` Node rows, "pools are sized from the
list"), but an action endpoint exists only as a `node/endpoint` string in
`actions.<a>.server|client`; a path's `output:` cannot name it as a declared
endpoint (the `wiring` warnings above).

### T9b. Transforms carry no timing or ownership

| Claim | Verdict | Evidence |
|---|---|---|
| interceptor reads TF | True, **on publish only** | `play_launch_interception/src/tf.rs:120-145` (frame pair, stamp, value hash per transform), registered at `lib.rs:1083` for `tf`/`tf_static`; `plugins/tf.rs` ships one `TfEdge` per (publisher, pair) per second |
| a contract cannot bound a pair's age or name its publisher | True | no frame vocabulary in `field_table.rs`; 0 contracts mention `/tf` in any corpus (table below) |
| run-time health exists without a contract | True, with fixed thresholds | `play_launch/src/health/tf.rs`: `tf_two_parents`, `tf_two_publishers`, `tf_disconnected`, `tf_stale` (2 s or 5 intervals, `:24`), `tf_static_at_rate`, `tf_never_moves` |

Not in the issue text, and it shapes the design: the age that breaks a node
is the age **at lookup** (`lookupTransform` in the consumer), which the
interceptor cannot see. It sees the stamp and the gap at publish. A
consumer-side age needs a hook on tf2's `BufferCore::lookupTransform`
(mangled C++ in `libtf2.so`, shared by rclcpp and rclpy) — possible, ABI
fragile. Publish-side age plus the inter-publish gap bound the lookup age
from above for "latest" lookups, which is what a contract can hold.

Practice (sources at end): Nav2 bounds actions on the CLIENT side —
`default_server_timeout` 20 ms (BT node waits for goal acceptance),
`action_server_result_timeout` (10 s on controller/behavior servers, 900 s
on bt_navigator: discard a goal with no result); progress is supervised by
a progress checker on odometry (`movement_time_allowance` 10 s), not by
feedback rate. MoveIt bounds the result relative to the goal
(`allowed_execution_duration_scaling` 1.2, `allowed_goal_duration_margin`
0.5 s): the result time is goal-dependent, not a constant. Nav2's
`transform_tolerance` is a CONSUMER parameter per node.

## Methods — actions

| | Change | Size | Breaks | Migration | Risks |
|---|---|---|---|---|---|
| **A1. Parts on the declaration** (doc's method 1): `actions.<a>.goal/feedback/result: {...}` lowered onto service/topic rules | grammar: 3 sub-contexts on `Context::Action`; model: per-action timing; walk: cross `index.actions` | M | nothing (additive) | none needed | puts requirements on the INTERFACE, while services put them on endpoints (`srv.<ep>.max_response`, `cli.<ep>.timeout`): two places for one kind of fact, the T3 problem again. One action, several servers, one bound |
| **A2. One bound** (doc's method 2): `actions.<a>.max_result`, charged like a blocking call | one key, walk edge | S | nothing | none | coarse: no acceptance vs execution split, no failure branch (no client timeout/fallback), so `call-unbounded` has no action analogue; a goal-dependent result time (MoveIt) has no honest constant |
| **A3. Action endpoints mirroring `srv`/`cli`** (service-contracts.md "Decided at evaluation", rlm `docs/design/service-contracts.md:306-311`): server endpoint `act_srv.<e>: { max_accept, max_result, stale_after, idempotent }`, client endpoint `act_cli.<e>: { call, timeout, on_timeout, on_rejected, result_timeout, on_result_timeout }`, declaration keeps wiring only | grammar: two node maps + 2 endpoint contexts; model: endpoint timing like `SrvContract`/client facts; walk: action edge = call (accept) then async result; rules: reuse `call-*` with an action prefix; nano-ros: pool sizing from the node lists (today from `structure.actions`) | M-L | `actions.<a>.call` moves to the client endpoint (deprecate one release, `migrate` copies it to each listed client, as G3 did for `max_transport`) | rewrite is mechanical | larger surface; nano-ros mirror PR |
| **A4. Cancel as the reaction edge**: on A3, `act_cli.<e>.cancels: true` on a path, and the server's `max_cancel` (cancel_goal response + the effect) charged | small on top of A3 | S | none | none | the one action use that is likely to sit ON a reaction route (MoveIt stop, Nav2 behaviour preemption) |
| **A5. Defer** (the 2026-10-30 decision) and fix the fallback only: make `reaction-unreachable` name the action it stopped at, and stop dropping the settle | resolve only | XS | none | none | leaves Nav2/MoveIt contracts unable to state a route; today 0 contracts need it |

Arithmetic for A3, matching phase 95's:
`success = max_transport + max_accept + max_result (+ result leg)`,
`failure = timeout (goal) or result_timeout x attempts + on_*'s route`,
`route = max(success, failure)`. Feedback rate needs no new rule if the
feedback stream can be addressed as a publisher endpoint (`min_rate_hz`),
but practice (Nav2) supervises progress on another topic, so feedback is
low value.

## Methods — transforms

| | Change | Size | Breaks | Risks |
|---|---|---|---|---|
| **F1. `transforms:` section** (doc's method 3): `<parent>/<child>: { max_age, publisher, static }` | grammar section; static check against publishers' declared frames; runtime from `TfEdge` | M | none | mixes a publisher FACT (who, static) with a consumer REQUIREMENT (age) in one place; one age for every consumer, while Nav2 sets tolerance per consumer |
| **F2. Predicate on `/tf`** (doc's method 4) | topic key with frame selector | S | none | `/tf` multiplexes every pair and several publishers; topic-level `rate_hz`/subscriber `max_age` are aggregates and wrong per pair. Agree with the doc: reject |
| **F3. Split by owner** (new): publisher fact `pub.<tf_ep>.frames: [map/base_link]` (+ `static: true` on the `tf_static` endpoint); consumer requirement `nodes.<n>.transforms: { map/base_link: { max_age } }`, `$(param transform_tolerance) s`-capable | grammar: one endpoint key, one node key; static rules: pair has exactly one publisher (`tf_two_publishers` statically), one parent per child (`tf_two_parents`), a consumer's pair is reachable through declared edges, a path that reads it is charged like a `state:` input; runtime: `TfEdge` gap and publish-side age against each consumer's bound | M | none | the lookup-side age stays unobserved (see T9b); composite pairs (map→odom→base_link) need the bound split over edges: the consumer's `max_age` is checked against the max over the edges' gaps |
| **F4. Health only**: keep TF a run-time concern, make `tf_stale` read a declared bound instead of 2 s | S | none | no static check, no route charge |

## Recommendation

| Issue | Pick | Why |
|---|---|---|
| T9a actions | **A5 now, A3 (+A4) when a contract needs it** — not A1 | 0 contracts and 0 Autoware binaries use actions; the gap today is an error, not a silent pass, so nothing is unsafe. A1 contradicts where services put timing (endpoints); A3 is the shape service-contracts.md already decided and reuses phase 95's arithmetic and rules. Interceptor support exists already (probe). The fallback bug (settle dropped, criticality stopped) is a resolve fix worth doing regardless |
| T9b transforms | **F3**, not F1 | keeps rlm's fact/requirement split (frames are a publisher fact, tolerance is a consumer requirement, as Nav2 configures it); gives the two static rules health already runs at run time; reuses `TfEdge` without interceptor change. 0 contracts today, 18 Autoware consumers, so it is an addition with no migration |

Contradictions with grammar-revision.md: (1) "is not charged" — it is
`reaction-unreachable`, an error, with a fallback that understates by the
settle; (2) the leaning "1 for actions" conflicts with
service-contracts.md's recorded shape (`act.<e>` endpoints) and with where
every other timing key lives; (3) the leaning "3 for transforms" puts a
consumer requirement on a shared declaration.

## Open questions

1. Is goal-dependent result time (MoveIt's scaling) stated as a constant
   `max_result`, or as a ratio of a goal field (a T8 predicate)?
2. Does feedback deserve any key, given practice supervises progress
   elsewhere?
3. Endpoint map names: `act_srv`/`act_cli` vs one `act:` with a role.
4. F3: is a consumer-side tf2 lookup hook wanted, or is publish-side age the
   contract's definition of "age"?
5. Should a frame pair be addressable in `monitors:` (a hazard on a stale
   `map/base_link`)? F3 makes it possible; nothing requires it yet.
