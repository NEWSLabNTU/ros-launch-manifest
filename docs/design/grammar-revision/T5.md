# T5. One word, several meanings

Exploration for `ros-launch-manifest/docs/design/grammar-revision.md` T5, against rlm
v0.3.14, play_launch `8f29baad`, nano-ros-pl `b7f7bae4c9`, island `addcefd`. Nothing here
is decided.

`ft` = `rlm/types/src/field_table.rs`. Contract counts are a YAML walk of 192 contract
files (rlm 35, play_launch 123, nano-ros 33, island 1), discovered with the predicate of
`rlm/scripts/key_inventory.py` (`T5-probe/discover.py`, `count_keys.py`, `counts.txt`).
Note: `docs/key-inventory.md` was generated at older commits and counts island 16
contracts; the island's tracked tree has one (`safety_island.contract.yaml`, 1256 lines).

## Issues (verified)

| Word | Claim | Verdict | Evidence |
|---|---|---|---|
| `reaction` | five things | **Confirmed: four target kinds in seven contexts.** | node path: `on_violation.reaction` (`ft:1330`); event chain: `hazards.reaction` (`ft:1228`), `modes.reaction` (`ft:1282`); mode **or** chain by lookup: `on_timeout.reaction` (`ft:1699`), `on_rejected`/`then` (`ft:1729`, `CallReaction`); path **or** chain: `supervise.reaction` (`ft:1592`), `links.monitor.reaction` (`ft:1647`). Where a mode is meant, hazards/supervise/links use `enters:` but clients put it in `reaction:` — **22 of 23 written `on_timeout.reaction` values name a mode.** 2 `hazards.reaction` values name a mode (the deprecated spelling, T1). |
| `drop` | loss vs speed | **Confirmed.** | loss: `topics.drop` (`ft:792`), event chain `drop` (`ft:971`); speed: `early.drop` (`ft:1673`). The speed `drop` also has its own unit parser (`parse.rs:1146`). |
| `within` | FRTI share vs time since command | **Overstated.** Both are a deadline measured from an event (`on_violation.within` is `BoundKind::Deadline`, `bound.rs` BOUND_KEYS; `early.within` "when the check runs, from the safe state's command", `ft:1667`). Same sense, different anchor event, as `ftti` and `max_latency` are. | |
| `response` | actuation vs service deadline | **Overstated.** `settle.response` (`ft:1463`) and `max_response` (`ft:697`) are both "time from a command/request to its effect/answer"; the keys differ (`max_` prefix) and live in different contexts. The vehicle wording of `settle.response` is T4's issue. | |
| `monitor` | four meanings | **Partly.** Keys: `hazards.monitors` (watched topics, `ft:1204`) and `links.monitor` (`ft:1641`, reserved, 0 writes, deleted by T1). `supervise` is a different word. "Run-time observer" is not a key. The real clash is cross-repo: nano-ros's "contract monitors" (`nros-orchestration-ir/src/contract_monitors.rs`) are the on-target budget/rate checkers, which the contract calls `supervise`. | |
| `functions` | not IEC 61508's safety function | **Confirmed.** `ft:402`: "Named guard groups: what a set of topics together provides". IEC 61508-4 3.5.1: a safety function is the function "intended to achieve or maintain a safe state ... in respect of a specific hazardous event", i.e. detect + react; play_launch's own guide uses it that way (`docs/guide/safety-function.md:1-3`). | |
| `criticality` | no standard behind `high/medium/low` | **Half.** The ordinal concept has one: mixed-criticality scheduling (Vestal, RTSS 2007; Burns & Davis, "Mixed Criticality Systems: A Review") uses criticality levels as an unnamed order. The three NAMES have none. Already `Kind::Consequence` (`ft:533`); written 13 times (pl only, 11 files: 11 `high`, 2 `low`). | |

## Methods

### Method 1 — one word per role (`enters:` for a mode, `runs:` otherwise)

| Aspect | Assessment |
|---|---|
| Change | `reaction` → `runs` in 6 contexts (path, chain, path-or-chain); `on_timeout`/`on_rejected` split into `enters`/`runs` like hazards; `functions` → `capabilities`; model unchanged |
| Size | rlm: ~14 field rows, parse (~6 sites), `migrate` (~120 lines; precedent `hazard-reaction-enters`, `migrate.rs:51`), `rule_names` paths; play_launch: messages (~40 strings) |
| Writes rewritten | 312 `reaction` (307 pl, 5 island), 99 function entries in 50 sections (+ every `monitors:` value naming a function is unchanged: it names the entry, not the key) |
| Migration | Fully mechanical: a mode is known in the same file (22/22 `on_timeout` mode targets resolved this way in the probe), so `migrate` can choose `enters` vs `runs` |
| nano-ros | tag bump only (no contract writes these keys; model kept) |
| Risk | `runs` reads as "executes" for a node path (accurate) and an event chain (a requirement, not code — slightly off). Alternatives: `then:`, `starts:`. Three-release schedule (`standard-names.md` §6) means two releases with both spellings |

### Method 2 — typed references (`reaction: mode/stopped`)

Every value changes (312 + 75 `enters`), and a prefix with `/` collides with the
`<node>/<subscriber>` syntax of `observes` and the `node/path` keys of the model; a chain
name may contain dots (`safety.stop`), so the prefix must be unambiguous. One key, but
the lookup ambiguity it removes is already removed by `enters` vs `reaction`. Cost similar
to method 1, gain smaller.

### Method 3 — docs only

Free. The field-table rows already say what each `reaction` targets; the trap is that
`on_timeout.reaction` takes a mode while `hazards.reaction` refuses one (deprecated), which
no doc fixes.

### Method 4 — let other topics remove clashes

| Clash | Removed by | Correct? |
|---|---|---|
| `early.drop` | T4 method 1 (extension key) or T4 method 5 (`decrease`) | yes |
| `early.within` | grammar-revision says T4 method 1 removes it | **No: T4 method 1 keeps `supervise.early: { within }` in the core.** And it is not a clash (see Issues). |
| `links.monitor` | T1 | yes |
| `settle.response` | T4 method 2 | wording only; not a clash to begin with |

### Method 5 (added) — `criticality` as an integrity level

For the underivable case (a node no hazard reaches), let the label be a level of the
contract's integrity scale (`criticality: ASIL_B`), mapped through the existing
severity-to-criticality map (rlm `types::integrity`, `Criticality::from_severity`).
13 writes to migrate (11 `high`, 2 `low`); the map's inverse is not unique (several levels
map to one criticality), so `migrate` must ask or pick the lowest level per bucket. Gains:
one vocabulary for "how much this matters". Costs: a node reached by no hazard is
arguably QM by definition, which makes the label meaningless or a contradiction.

## Recommendation

| Word | Recommendation | Reason |
|---|---|---|
| `reaction` | **Method 1**, contract keys only, model fields kept | Mechanical migration, 0 nano-ros contract edits, removes the client-side mode/chain lookup |
| `functions` | **Method 1** (`capabilities`), same release | 50 sections, mechanical; the IEC 61508 clash is real and the guide already uses the standard sense |
| `drop` (speed) | via T4 | |
| `within`, `response` | **No rename** | One sense each |
| `monitor` | T1 deletes `links.monitor`; document the nano-ros "contract monitor" vs contract `monitors` difference | |
| `criticality` | **Keep** (consequence); open whether method 5 is worth it | |

Batch every rename into one R release with T6 (one `migrate` pass, one nano-ros bump).

## Open questions

1. `runs:` or another verb (`then:`, `starts:`)?
2. `capabilities`, `signals` or `provisions` for `functions`? (A function is a topic group a
   mode requires; `signals` loses the "together provide" sense.)
3. Rename the model fields too (consistency) or never (zero nano-ros code)? This document
   assumes never.
4. Should `on_timeout`/`on_rejected` keep accepting a mode under the old key for the R
   release (it is the majority use: 22 of 23)?
