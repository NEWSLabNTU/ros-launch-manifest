# T10. Deployment beyond one host

Explored 2026-11-13 against rlm v0.3.14 and play_launch main (8f29baad).
Probe: `play_launch/tmp/grammar-revision/T10-probe/` (the `multihost` fixture with a
contract naming both hosts' nodes and two `independence` entries, checked
with `host:=robot1` and `host:=all`).

## Issues (verified)

| Claim | Verdict | Evidence |
|---|---|---|
| `independence` cannot say `host` | True, refused with a reason | rlm `types/src/parse.rs:1797-1803`; table row `field_table.rs:1777`; decision 3 in `docs/design/fault-tolerance.md:247-261` |
| one resolved model runs on one host | True: `Deploy` has no host (`model/src/lib.rs:2382-2400`, it keeps `domain`, `locator`, `rmw` per node) | CLAUDE.md 2026-07-31; `tests/tests/resolve_multihost.rs::a_launch_only_resolve_produces_no_deploy_entries` |
| two-machine redundancy is not checkable | True, and worse than "not checkable": a partitioned check **passes it vacuously** | probe below |

Probe results (`play_launch check multihost.launch.xml host:=<h>`):

| Contract writes | `host:=robot1` | `host:=all` |
|---|---|---|
| node key `robot2/talker2` (relative) for a node on the other host | `error[node-identity-unknown]` | same error (relative key mis-qualified) |
| node key `/robot2/talker2` (absolute) | **accepted, no diagnostic**; the node is not in the model | accepted |
| `independence: of [/robot1/talker1, /robot2/talker2], not_sharing: [process]` | **passes**: `/robot2/talker2` is absent, so `pairs()` finds no shared process (`resolve/src/ros/independence.rs:81-160`, no absent-node check) | passes, both in the model, separate processes |
| `/hub/hub`, unconditioned, runs on BOTH hosts | not reported | not reported (one node in a one-host model) |

So today an author can write a cross-host independence requirement and get
a clean verdict from a model in which one side does not exist. That is the
concrete defect T10 should fix first, whatever the method.

Further facts that matter:

- `cpus` is checked against ONE platform file (`independence.rs:11-15`);
  CPU 2 on host A and CPU 2 on host B are the same number. Checking an
  `host:=all` model with one platform file would report a false
  `independence-violated` for `cpus`, or apply one host's file to the other.
- Cross-host hops are already modelled, one model at a time: `external:`
  marks a side outside the image, `links:` (rlm v0.3.4, `field_table.rs:460,
  1620-1660`; design `docs/design/links.md`) carries a measured, sourced
  `max_transport` and `clock: synced | unsynced`, and a subscriber names its
  link (`sub.<ep>.link`).

### How the island models its second host today

`simple-autoware-safety-island/src/safety_island_bringup/launch/
safety_island.contract.yaml` (1,256 lines) is ONE contract over ONE launch
(three MRM nodes, `safety_island.launch.xml`). The Autoware PC is outside:
18 `external:` lines mark host-side ends; 3 `links:` (`gate_availability`
56 ms, `localization_kinematic_state` 36 ms, `gateway_control_mode` 143 ms,
each measured on board runs, `clock` unsynced) charge the UART hop on the
guard edges. What it cannot say, in its own words:

- `reaction-unguarded` acknowledged twice (`:452-466`): "only Autoware or the
  vehicle outside this image could notice a stalled manoeuvre, and nothing
  there is declared yet": the watcher of the watcher is on the other host.
- Its hardware independence from the HPC, the reason the island exists, is
  stated nowhere (no `independence:` key; `host` is refused).
- End-to-end chains through the host are checked in "the demo composition
  contracts" (`rtss-work-2026-demo:demo/l3/contracts/`, three files, cited at
  `:346, :431` and `docs/boot-through.md:622`; that repo is not on this
  machine): the island plus the host's `vehicle_cmd_gate` composed into ONE
  tree and checked as one model, with links on the crossing hops. That is a
  fourth method nobody named: **one all-hosts model with links**.

## What cross-model checks need

| Check | Needs | Exists today |
|---|---|---|
| `not_sharing: [host]` | node → host map | no host anywhere |
| independence names only nodes that exist somewhere | union of node sets | no; absent node passes |
| a node runs on two hosts (unconditioned in a partitioned launch) | union, by FQN | no |
| cross-host wiring: an `external: sub` on A matched by a real subscriber on B | union of topic graphs | no; each side is `external` |
| a chain spanning hosts (island availability → handler → host gate → vehicle) | union graph + the link on each crossing | only by composing one tree (demo) |
| `reaction-unguarded` closed by a guard on the other host | union graph | no (acknowledged in the island) |
| `cpus` per host | platform file per host | one per check |
| clocks | `links.clock` | yes |

## Methods

| | Change | Size | Breaks | Migration | Risks |
|---|---|---|---|---|---|
| **H0. Close the vacuous pass** (prerequisite for all): an `independence` entry naming a node absent from the model is `independence-unchecked` (not a pass); an absolute node key absent from the launch is reported like a relative one | resolve only | XS | contracts naming another host's node by absolute key now warn | none | none; it makes the current gap visible |
| **H1. System of models** (doc's method 1): a file naming per-host resolved models and links; checks over the set | new top-level artifact; rlm type; check over N models; links bind endpoints across models; per-host platform files | L | none (new) | none | a second artifact beside the SystemModel, after Phase 46/47 made the model the ONE artifact; mixed realizers (the island is nano-ros/Zephyr, the PC play_launch/Linux) must agree on one schema version |
| **H2. Partitioned resolve** (doc's method 2): `check --hosts a,b` resolves one launch per `host:=` and checks the union | check verb; host map from the partition; `SharedFact::Host` | S-M | none | none | **cannot express the island**: two launch trees, two realizers, two platform files; knows only what the launch's conditions say; an unconditioned node lands on every host (the multihost guide's own "runs on every host") |
| **H3. Stay single-host** (doc's method 3): argue independence outside, cite it in `requirement.source` | none | 0 | none | none | today's state plus H0; the island's whole rationale stays prose |
| **H4. One all-hosts model + links** (what the demo does): compose every host's launch into one tree, mark crossings with `link:`, add a host per node | `Deploy.host` back, set by the composing launch (an `<arg>`-driven group, not `machine=`), per-host platform file | M | re-adds what 2026-07-31 removed (but from a legal ROS 2 source, not `machine=`) | none | process/container/cpus facts must become per-host keys; a model no single host runs (`up` must refuse or partition it) |
| **H5. H2 generalised by a hosts list (new)**: `check --system hosts.yaml`, where `hosts.yaml` is INPUT to check only: `{ <host>: { launch, args, sched } }`; each entry resolved as today into its own model stamped `meta.host`; cross-model rules over the set; nothing new is written as an artifact | check verb + a small input type; `meta.host` in the model; `SharedFact::Host`; union-graph rules reuse the existing walk over a merged index with links on crossings | M | none | none | merging N indexes must keep scope ids apart; links on both sides must agree (one `link:` name, one bound); nano-ros must stamp `meta.host` on its model for the island to join |

H2 is H5 with one launch file and the host as an argument, so H5 subsumes
H2 at small extra cost and covers the island (different launch files and
platform files per host). It differs from H1 in that the per-host models
stay the only artifacts and the hosts list is a check input, like
`--sched`, not a deployable file.

## Recommendation

1. **H0 now**, independent of the rest: it is a correctness fix (a clean
   verdict over a node that is not there), small, and needed by every
   method.
2. **H5** as the first real step, not plain H2: the motivating system (the
   island) is two launch trees on two realizers, which H2 cannot express;
   H5 costs one input type more and keeps the SystemModel the one artifact.
   Its first rules: `not_sharing: [host]`, node-on-two-hosts, cross-model
   wiring of `external:` sides, `cpus` per host, then chains across links.
3. H1 only if a deployable multi-host artifact is wanted (an orchestrator
   that starts every host from one file); nothing asks for that today.
   H4 is what the demo does by hand and should be read as evidence for the
   need, not as the method: it re-adds a per-node host to a model `up` runs
   on one host.

Contradictions with grammar-revision.md: the issue as written ("not
checkable") understates the present state — a partitioned check passes a
cross-host independence vacuously (H0); and the leaning "2 as the first
step" does not cover the one real multi-host system in the corpus, which has
two launch files and two realizers.

## Open questions

1. Does `meta.host` belong in the model (one string per model), or only in
   the hosts list? The model is what nano-ros reads; stamping it there lets
   a realizer refuse a model meant for another host.
2. Should `host` join `not_sharing` as a fourth fact, or should cross-model
   independence be implied by being in different entries of the hosts list
   (with `not_sharing: [host]` only checking that)?
3. Power supply, network switch, shared sensor: decision 3 kept them out
   because play_launch has no such facts; a hosts list could carry them as
   stated (unchecked) facts. In or out?
4. Links named on both sides: one `links:` section in the hosts list, or each
   model keeps its own and the check requires them to agree?
5. Is the rtss-work demo's composition approach to be retired once H5
   exists, or kept as the way a chain across hosts is costed?
