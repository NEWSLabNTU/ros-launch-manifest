## 1. Issues (verified)

| # | Claim in grammar-revision.md | Verdict | Evidence |
|---|---|---|---|
| 1a | `on:` covers five of EN 50159's seven threats; corruption and masquerade are missing | **Correct, with a caveat** | `FaultKind` = omission, late, loss, reported, overrun, repetition, resequencing, insertion (rlm `types/src/types.rs:1104-1125`); `parse_fault_kind` accepts seven, refuses `overrun` in `on:` (`types/src/parse.rs:2089-2115`). No corruption/masquerade anywhere. Caveat below (1d): the three "communication" classes are judged on the SENDER, not the channel. |
| 1b | No end-to-end protection (CRC, counter, data ID) can be named | **Correct** | No key in `field_table.rs` names a counter, CRC or data ID. Grep for `crc`/`counter`/`checksum` in rlm `types/` returns nothing relevant. |
| 1c | Corruption was not adopted because "not observable above DDS (DDS checks its own frames)" | **Overstated** | `fault-tolerance.md:84,210,267`. RTPS has no mandatory message checksum: the UDP checksum is 16-bit and optional on IPv4; RTPS 2.5 added an *optional* checksum in the HeaderExtension submessage (CRC-32C/CRC-64/MD5), which RTI Connext 7.3 emits by default; Fast DDS support not found; the shared-memory transports (Fast DDS SHM, Iceoryx) carry no checksum at all. And on one host the dominant source of corruption is not the wire: it is the publishing or receiving software (a memory fault, a wrong field written). That is exactly what AUTOSAR E2E guards against **on the same ECU**, since it runs between software components. So "not observable above DDS" holds for the observer, not for the threat. |
| 1d | (new) Run-time `repetition`/`resequencing` judge the PUBLISHER, not the channel | **New finding** | Checked only on `EventKind::Publish` of a guard (`play_launch/src/runtime_enforcement/mod.rs:1198-1243`), keyed `(topic, publisher handle)` and compared with `header.stamp`. A take-side repetition (the channel) is never judged. Within one DDS writer, RTPS sequence numbers already discard duplicates and (for reliable) reorder, so channel repetition/resequencing is largely defended by DDS itself; what the rule actually catches is an application re-sending an old stamp. |
| 1e | (new) Stamp-equality reads a legitimate state re-send as `repetition` | **New finding** | play_launch's own `stale_stamp` info (phase 88, CLAUDE.md) observed Autoware re-sending one stamp at rate on gear command, operation mode and the emergency stop operator's control command: "right for a state, wrong for data". `on: [repetition]` on such a topic would fire on correct behaviour. A counter (incremented per send) has no such ambiguity. |
| 1f | (new) An unstamped guard topic is never judged for repetition/resequencing, silently | **New finding** | `stamp` is `None` when sec = nsec = 0 (`mod.rs:1192-1193`) and the class check is skipped. No static rule warns that a topic named under `on: [repetition]` has no `header.stamp`/`stamp` (grep of `value_rules.rs`, `manifest_loader.rs`: none). |
| 1g | (new) `insertion` cannot see a masquerade or a foreign process | **New finding** | `judge_publisher` compares FNV-1a of the declaring node's NAME (`mod.rs:1477`) with the creating node's; it runs on `PublisherInit` from an instrumented process (`mod.rs:680`). A second node using the declared node's name (ROS 2 allows duplicate names, it only warns) passes; a publisher in a process play_launch did not start (another host, a bag player run separately) produces no event at all. So `insertion` today is "an unexpected node in a launched process", not EN 50159 insertion and not masquerade. |
| 1h | (new) The default of an omitted `on:` is stated three ways | **Side finding** | rlm doc comment: "every class" (`types.rs` HazardDecl.on); play_launch message: "omission, late and loss" (`value_rules.rs:572-575`); nano-ros: the five pre-v0.3.13 classes (`nano-ros-pl/packages/core/nros-orchestration-ir/src/ftti_budget.rs:235-254`). Adding a class makes this worse unless one definition is fixed first. |

### Static credit today

The three communication classes are credited exactly one way: an
`on_violation` with `mechanism: application` on a subscriber, charged as 0 ms
detection (`resolve/src/ros/manifest_loader.rs:1851-1855`, message at
`:1943-1945`). That is grammar-revision.md's method 2, already shipped for
repetition/resequencing/insertion in v0.3.13.

## 3. Prior art

**AUTOSAR E2E** (PRS E2EProtocol R22-11, glossary Table 2.1, mechanism tables 6.12-6.93):

| Mechanism | Detects (Table 6.13, Profile 1) |
|---|---|
| Counter | repetition, loss, insertion, incorrect sequence, blocking |
| Regular transmission + timeout | loss, delay, blocking |
| Data ID + CRC | masquerade and incorrect addressing, insertion |
| CRC | corruption, asymmetric information |

| Profile | CRC | Counter | Data ID |
|---|---|---|---|
| 1 | 8 (SAE J1850) | 4 bit | 16, implicit (in CRC only) |
| 4 | 32 (0xF4ACFB13) | 16 | 32 explicit, + 16-bit length |
| 5 | 16 (0x1021) | 8 | 16, implicit |
| 6 | 16 | 8 | 16, implicit, + length |
| 7 | 64 (ECMA) | 32 | 32, + 32-bit length |
| 11 | 8 | 4 | 16 implicit or 12 split |
| 22 | 8 (0x2F) | 4 | list of 16 IDs keyed by counter |

Two consequences for a contract key: (i) a Data ID is often NOT a message
field (implicit: folded into the CRC), so `id:` must accept a constant, not
only a field; (ii) counters are 4 to 32 bits and may share a byte, so the
wrap modulus cannot always be inferred from the field type. The receiver
state machine also has a tolerance (`MaxDeltaCounter`: OKSOMELOST vs
WRONGSEQUENCE) that a contract would want to state.

**EN 50159:2010** defines three transmission categories (cat. 1 closed and
fixed; cat. 2 partly unknown, no unauthorised access; cat. 3 open, access
possible) and a threats/defences matrix (Table 1). The sample preview
(iTeh, `en50159.txt`) gives the definitions (safety code 3.1.48, masqueraded
message 3.1.30, MDC 3.1.29) but stops before the matrix; the matrix below is
the commonly reproduced one, **not verified against the primary text**:

| Threat | Seq. no. | Time stamp | Time-out | Src/dst id | Feedback | Ident. proc. | Safety code | Crypto |
|---|---|---|---|---|---|---|---|---|
| Repetition | X | X | | | | | | |
| Deletion | X | | | | | | | |
| Insertion | X | | | X (src) | X | X | | |
| Resequencing | X | X | | | | | | |
| Corruption | | | | | | | X | X |
| Delay | | X | X | | | | | |
| Masquerade | | | | | X | X | | X |

Masquerade in cat. 3 needs cryptographic techniques; a non-cryptographic
data ID only covers cat. 1/2 (accidental mis-addressing, not an attacker).

**ROS 2 practice.**

| Source | What carries a counter / CRC / id |
|---|---|
| `std_msgs/Header` | ROS 2 removed ROS 1's `seq` (common_interfaces; ROS Answers 418217). No standard counter. |
| `rmw_message_info_t` (Humble `rmw/types.h:565,583`) | `publication_sequence_number` per writer + `publisher_gid`, at take, no message change. Middleware-assigned, so it detects channel loss/repetition/reorder and identifies the writer, but not an application re-sending stale data. Fast DDS fills it; an rmw without it returns `RMW_MESSAGE_INFO_SEQUENCE_NUMBER_UNSUPPORTED` (`:525`). Cyclone on Humble not verified. The interceptor does not read it today. |
| Autoware 1.5.0 | `autoware_adapi_v1_msgs/Heartbeat`: `uint16 seq` "for order verification, wraps at 65535". `continental_msgs/ContinentalSrr520ObjectList`: `uint8 sequence_counter`, `uint32 cycle_counter` (from the radar's CAN E2E). No CRC field in any of 454 packages' messages. |
| Humble `/opt/ros/humble` | `septentrio_gnss_driver/BlockHeader: uint16 crc` (the receiver's wire CRC, passed through). `visualization_msgs` `sequence_number` (bookkeeping, not safety). |
| safety island | Its own heartbeat trace record has a monotonic `seq` (`safety_island_tracing/include/island_trace.h:22-26`), not a ROS message. |
| SROS2 / DDS Security | Authentication + access control (a named enclave may publish a topic) + GMAC/AES-GCM per message: covers corruption and masquerade on the wire, cat. 3 strength. Not on intra-process or (typically) SHM paths. |

So: counters exist in practice on a few safety-adjacent messages; CRCs in
ROS messages are rare and are pass-throughs of a device's own E2E; nobody
uses a ROS-level data ID.

## 5. Recommendation

| Issue | Recommend | Why |
|---|---|---|
| Name the E2E mechanism (1b) | **M1 with M1' subkeys**, presence-checked; `counter` judged at run time | Smallest addition a safety argument can cite; matches AUTOSAR's three mechanisms; counter verification costs one existing field read. |
| Counter vs stamp (grammar-revision's open question) | **Counter replaces stamp** for `repetition`/`resequencing` whenever `protected.counter` exists | 1e: stamp equality is wrong on state topics; a counter is per send by definition. Keep stamp as the fallback, and add a static warning for 1f (class asked on an unstamped type with no counter). |
| Corruption (1a/1c) | **M2 for the class**, but only together with M1: `on: [corruption]` requires `protected.crc` or `mechanism: application` | Gives the class a checkable precondition instead of a pure claim. Correct the "DDS checks its own frames" sentence in `fault-tolerance.md` §4.6 either way. |
| Masquerade (1a/1g) | **M3 (`id`) for cat. 1/2; M5 deferred** | Mis-addressing via remaps is the realistic on-host case; cryptographic masquerade belongs to SROS2 and should be stated, not modelled, until a user needs it. Rename or document `insertion` as "unexpected node in a launched process" (1g). |
| Default of omitted `on:` (1h) | Fix ONE definition before adding classes; new classes never enter the default | Otherwise every one of 113 hazards changes meaning. |
| Channel-side checks | M6 as a later run-time improvement, not grammar | No key needed; useful evidence; rmw-dependent. |

## 6. Open questions (human decision)

1. Is `crc` worth a key when it can only be checked for presence? (The
   alternative: `counter` and `id` only, corruption via
   `mechanism: application`.)
2. Category: should a contract state its EN 50159 category (1/2/3) so the
   checker can demand crypto (M5) for cat. 3? No user today.
3. Does `masquerade` become a class of its own, or does `insertion` keep
   both meanings with `id` deciding the strength?
4. Should run-time comm classes be judged at the receiver (take) as well as
   the sender? Today the observer judges only publishes (1d).
5. Where `protected:` lives: on `topics.<t>` (one fact per topic, the
   writer and all readers agree) or on the publisher endpoint (AUTOSAR
   configures per data element, i.e. per topic). Leaning per topic.
